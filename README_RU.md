# nbdproxy

[English](README.md) | Русский | [简体中文](README_CN.md) | [Español](README_ES.md) | [Français](README_FR.md)

Небольшой NBD-прокси без внешних зависимостей, который сохраняет **локальное клиентское соединение открытым**, переподключаясь к перезапущенному серверу. Поддерживает TCP и Unix-сокеты с обеих сторон. Linux `nbd-client` не требует `-persist` или поддержки переподключения через netlink, в том числе в версии 3.26.1.

```text
Linux /dev/nbd0 ── stable local socket ── nbdproxy ── reconnect ── NBD server
```

Предназначен для локального сервера, например s3nbd, который перезапускается независимо от прокси. Один процесс предоставляет один настроенный экспорт **одному клиентскому соединению**. Запросы выполняются в порядке поступления; одновременно обрабатывается не более одного запроса к серверу. Это сознательный обмен пропускной способности на простой порядок повторного выполнения.

## Сборка и запуск

Требуется Go 1.24 или новее; внешние модули и библиотеки C не нужны.

```sh
go build -trimpath -o nbdproxy .
./nbdproxy -version
sudo install -d -m 0755 /run/nbdproxy
sudo ./nbdproxy \
  -listen unix:/run/nbdproxy/nbd.sock \
  -upstream tcp:127.0.0.1:10809 \
  -export disk1
```

В другом терминале на Linux:

```sh
sudo modprobe nbd
sudo nbd-client -unix /run/nbdproxy/nbd.sock /dev/nbd0 -N disk1 -b 4096
```

Используйте **одно соединение**, без `-C 2`. Для перезапусков сервера `-persist` не нужен. Избегайте конечного тайм-аута NBD I/O в ядре, если простой может длиться дольше: тайм-аут запроса ядра способен завершить I/O с ошибкой, даже когда локальный сокет остаётся открытым. Для существующего устройства проверьте `/sys/block/nbd0/queue/io_timeout` (миллисекунды, если ядро предоставляет этот параметр). Нулевой `nbd-client -timeout` оставляет текущее значение или значение ядра по умолчанию; это ненадёжный способ сбросить тайм-аут, ранее заданный для повторно используемого устройства. Проверьте фактическую настройку ядра.

Пример TCP на стороне клиента и Unix-сокета на стороне сервера:

```sh
./nbdproxy -listen tcp:127.0.0.1:10810 -upstream unix:/run/s3nbd/nbd.sock -export disk1
sudo nbd-client 127.0.0.1 10810 /dev/nbd0 -N disk1 -b 4096
```

Ни на одной стороне нет аутентификации или TLS. Ограничьте TCP-прослушивание loopback-интерфейсом либо доверенной изолированной сетью. Клиентский Unix-сокет создаётся с правами 0600. Родительский каталог должен существовать. Существующий путь сокета не удаляется автоматически при запуске: при необходимости проверьте и удалите оставшийся сокет вручную. При штатном закрытии Go удаляет сокет Unix-слушателя.

## Что переживает перезапуск

1. Прокси согласует настроенный экспорт с сервером до завершения согласования с клиентом. Если при первом подключении сервер недоступен, согласование откладывается: начальное подключение `nbd-client` всё ещё может завершиться по тайм-ауту и потребовать повтора.
2. Во время передачи каждый запрос и его данные WRITE остаются в памяти до получения полного ответа сервера. Частичный ответ READ отбрасывается.
3. При ошибке подключения, согласования, транспорта или тайм-ауте серверного I/O прокси выжидает и переподключается без ограничения числа попыток. Локальный клиентский сокет остаётся открытым. Ответы NBD с ошибкой от сервера передаются клиенту без повтора.
4. При переподключении размер и флаги передачи сервера должны точно совпадать с исходными. Несовпадение завершает клиентскую сессию, чтобы не повторять запрос на несовместимом экспорте. Настроенные адрес и имя должны по-прежнему указывать на **то же хранилище**: в NBD нет обязательного постоянного UUID экспорта, поэтому проверки размера, флагов и имени не обнаружат подмену другим диском того же размера.
5. Ожидающий запрос повторяется до отправки любого следующего запроса.

Гарантия повтора — **как минимум один раз**, а не ровно один раз. WRITE мог выполниться до потери ответа. Повтор безопасен, только если старая операция сервера уже не может выполниться позже, после новых операций. Остановленный серверный процесс удовлетворяет этому условию; произвольные сетевые разделения, тайм-ауты живого или зависшего сервера и параллельные записи требуют гарантий fencing/сериализации на стороне хранилища. Не используйте прокси как универсальную распределённую систему переключения при отказе или совместно с другим писателем.

Журнала и постоянного кеша записи нет. Сервер, подтверждающий запись в энергозависимую память, может потерять её при сбое; прокси не восстановит запросы, которые уже подтвердил ядру. Гарантии сохранности FLUSH/FUA сервера по-прежнему важны. Для повтора также необходимо, чтобы реализации WRITE/TRIM сервера допускали безопасное повторное выполнение. Перезапуск или завершение **самого прокси** разрывает клиентское соединение и не покрывается механизмом переподключения к серверу.

## Протокол и ограничения ресурсов

- NBD fixed-newstyle; на клиентской стороне EXPORT_NAME, INFO, GO, LIST, ABORT.
- READ, WRITE, FLUSH, TRIM и согласованный FUA; только простые ответы.
- Согласование с сервером использует EXPORT_NAME с настроенным именем. Сервер должен принимать этот режим и подразумеваемые им ограничения размера блока (минимум 1 байт).
- Неподдерживаемые опции (включая структурированные ответы и TLS) получают ERR_UNSUP; неподдерживаемые команды/флаги — EINVAL. Экспорты только для чтения отклоняют запись.
- Возможность нескольких соединений маскируется, даже если сервер её объявляет. Второе клиентское соединение закрывается без согласования.
- Предел READ/WRITE: 32 МиБ на запрос. Один выполняемый запрос и один запрос предварительного чтения; буферизация TCP/сокета обеспечивает обратное давление. Буферы данных приложения ограничены примерно 96 МиБ на активную сессию (включая ответ чтения), независимо от длительности простоя. Диапазоны TRIM не несут данных.
- Неверная сигнатура, слишком большие опции/данные WRITE или отключение клиента завершают сессию. Клиент, который не заканчивает передачу запроса, может занять единственную сессию; это доверенный локальный сервис, а не публичная многопользовательская точка доступа.
- Ошибки сервера пишутся в stderr структурированным логгером Go. Некорректное согласование/ответ сервера приводит к повторным попыткам; для диагностики смотрите логи.

Параметры доступны через `./nbdproxy -help`:

| Флаг | По умолчанию | Значение |
|---|---|---|
| `-listen` | `unix:/run/nbdproxy/nbd.sock` | Локальный слушатель |
| `-upstream` | `tcp:127.0.0.1:10809` | Адрес сервера |
| `-export` | пусто | Имя экспорта с обеих сторон |
| `-retry` | `1s` | Фиксированная задержка между переподключениями |
| `-connect-timeout` | `5s` | Тайм-аут подключения к серверу |
| `-handshake-timeout` | `30s` | Тайм-аут согласования каждого соединения |
| `-io-timeout` | `1m` | Предельное время серверного запроса и записи ответа клиенту |

Предельное время серверного запроса вызывает переподключение, но не ограничивает общее время восстановления. При передаче прокси не устанавливает срок чтения с клиентской стороны, поэтому неактивные клиенты остаются подключёнными. SIGINT/SIGTERM закрывает слушатель и активную сессию, отменяет повторные попытки и завершает процесс. Перед остановкой прокси размонтируйте файловые системы и отключите NBD.

## systemd

Установите бинарный файл, измените upstream/export в готовом юните и включите его:

```sh
sudo install -m 0755 nbdproxy /usr/local/bin/nbdproxy
sudo install -m 0644 packaging/nbdproxy.service /etc/systemd/system/nbdproxy.service
sudo systemctl daemon-reload
sudo systemctl enable --now nbdproxy
sudo journalctl -u nbdproxy -f
```

Юнит использует DynamicUser, создаёт `/run/nbdproxy` и не требует привилегий root. Root может подключить `nbd-client` к сокету с правами 0600. Unix-сервер должен разрешать доступ пользователю сервиса; для такого развёртывания замените DynamicUser фиксированным пользователем/группой и настройте права сокета. Сохраняйте независимость юнита от серверного сервиса: не добавляйте PartOf/BindsTo, останавливающие прокси при перезапуске сервера. Restart=on-failure перезапускает процесс, но не сохраняет существующие NBD-сессии.

## Проверка

```sh
go vet ./...
go test -race ./...
go test -run='^$' -fuzz=FuzzExportName -fuzztime=10s
```

Тесты проверяют выполненные записи с потерянными ответами, частичные ответы чтения, порядок flush, изменения экспорта, отмену, некорректное согласование, валидацию запросов и фаззинг парсера. CI запускает тесты на Linux и macOS и собирает все релизные платформы. Задание Linux также подключает настоящий `/dev/nbd0` через системный nbd-client, выполняет прямой I/O, останавливает сервер, проверяет, что I/O остаётся в ожидании, перезапускает сервер и проверяет данные, последующие записи и flush.

Для ручного запуска этого интеграционного теста, перезаписывающего устройство, используйте **одноразовый Linux-хост со свободным `/dev/nbd0`** и установите nbd-client:

```sh
sudo modprobe nbd nbds_max=4 max_part=0
go test -c -o /tmp/nbdproxy.test
sudo env NBDPROXY_KERNEL_TEST=1 /tmp/nbdproxy.test \
  -test.v -test.run '^TestLinuxKernelRestart$' -test.timeout 60s
```

Тест записывает данные в `/dev/nbd0`. Он запускается только явно и пропускается при обычном запуске тестов. Тест с настоящим ядром не работает на macOS.

## Релизы

```sh
go install github.com/goreleaser/nfpm/v2/cmd/nfpm@v2.41.0
./scripts/release.sh v0.1.0
```

Создаёт архивы для Linux amd64/arm64 и macOS amd64/arm64 с автономным бинарным файлом, документацией, лицензией и юнитом systemd, DEB и RPM пакеты для Linux amd64/arm64, а также контрольные суммы SHA-256 всех артефактов в `dist/`.

После отправки репозитория на GitHub отправка тега `v*` запускает релизный workflow. Он выполняет vet и тесты, собирает архивы и пакеты и сразу публикует GitHub Release с автоматически сформированными примечаниями. CI и релизные workflow имеют только права чтения, кроме contents:write у релизного задания.
